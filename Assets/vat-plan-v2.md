# VAT-система для Unity 6000.3+ URP — план реализации

**Платформы:** iOS Metal (от iPhone 12), Android Vulkan и GLES 3.1+ (класс Adreno 650 / Mali-G78 и выше).
**Пакет:** `com.vatyakov`, `"unity": "6000.3"`. Alembic 2.4.5 — необязательная зависимость (§4).
**[проверить]** — факт, который подтверждается на устройстве в указанной подверсии (§5).

---

## 0. Решения

| Вопрос | Решение |
|---|---|
| Масштаб | До ~100 VAT-персонажей в кадре, у каждого свой GameObject с логикой |
| Состояние юнита | Отдельный материал на юнита + SRP Batcher. Хаков с инстансингом нет |
| MaterialPropertyBlock | Запрещён полностью — ни в патче 1, ни в патче 2 |
| Жидкости | В патче 1 — только с постоянной топологией, через Vertex-режим. Меняющаяся топология — патч 2 |
| Бленд | Только переход одного клипа в другой: кроссфейд по таймеру или вес перехода из кода (§1.5). Вложенных прерываний и долгих смесей нет |
| Материалы | Shader Graph поверх HLSL-ядра, нужны normal maps |
| TAA / motion blur | Возможны, поэтому motion vectors должны быть правильными (§3) |
| Длительность сессии | До 4 часов (§1.3) |
| Превью в редакторе | Клип по умолчанию на шаблонном материале (§1.6) |
| Хранение | `.asset` в бинарной сериализации (§1.8) |
| Порядок работ | Сначала минимальная Vertex-версия, дальше по одной возможности за подверсию, каждая проверяется отдельно (§5) |

## 1. Общее ядро

### 1.1 Адресация
- **X = элемент** (вертекс или тексел кости), **Y = кадр**. Все клипы ассета лежат в одной текстуре друг под другом, без padding-строк. **E** — число элементов, **F** — число кадров клипа.
- **Индекс — из Vertex ID** (нода SG), не из UV.
- **Ширина не степень двойки:** `W = ceil(E / ceil(E / 4096))`. В шейдере `uint b = id / W; uint x = id − b·W; row = b·totalRows + startRow + frame`.
- **Высота ≤ 4096 без исключений**, на ней держится упаковка клипа (§1.4). Если `blocks·totalRows > 4096`, бейк падает с сообщением: уменьшить fps или длину клипов либо разнести клипы по разным `VatAsset`. Кроссфейд возможен только внутри одного ассета.
- **baseVertex = 0 на всех сабмешах.** D3D и Metal исключают его из SV_VertexID, Vulkan и GLES включают. Поэтому запрещены static batching, dynamic batching и объединённые меши.

### 1.2 Точность
- **Текстуры с Blackboard** Shader Graph на мобилках читаются через mediump-сэмплер (Shader Precision Model = Platform Default, как в проекте). Поэтому VAT-текстуры — **только RGBAHalf и RGBA8**. fp32 точности не добавляет и стоит дороже, валидатор его запрещает.
- **RGBA8 читается как байты:** `round(v·255)` точен и через mediump.
- **Позиции хранятся смещениями от покоя:** в Vertex — от rest-меша, в Bone и Rigid — от позы покоя кости. Ошибка half тогда пропорциональна смещению, а не расстоянию до origin.
- **Пара hi/lo half** (`hi = half(p)`, `lo = half(p − hi)`) — только в `_VatDriftTex` (§1.9).
- **VAT-SubGraph и все Custom Function — Precision Single**, обёртки только `_float`. Иначе Vertex ID станет half и сломается выше 2048.
- **Инспектор показывает ошибку с учётом fp16-выборки**, а не точность хранения.

### 1.3 Индекс кадра и время

**Раскладка клипа:**
- **Loop:** `F = max(1, round(L·fps))`, `t_k = k·L/F`, `fps_eff = F/L`. Последний кадр не дублирует первый.
- **One-shot:** `F = round(L·fps) + 1`, `fps_eff = (F−1)/L`.
- `L ≤ 0`, `fps ≤ 0` или нечисловые значения — ошибка бейка.

**Время:** `f = (t − t0)·rate + offset`, где `rate = fps_eff·speed`.
- **Loop:** `offset` держится в [0, F).
- **One-shot:** `offset` в [0, F−1] без заворота, `normalizedOffset = 1` — последний кадр.
- **Сессия до 4 часов:** шаг `Time.time` там ≤ 1 мс. Тест формул на CPU с t = 4 ч.

**Кламп кадра** (приводить к int только после клампа):
- **Loop:** `u = f − F·floor(f·invF)`, `f0 = min(floor(u), F−1)`, `frac = saturate(u − f0)`, `f1 = (f0+1 ≥ F) ? 0 : f0+1`.
- **One-shot:** `fc = clamp(f, 0, F−1)`, `f0 = clamp(floor(fc), 0, max(F−2, 0))`, `frac = fc − f0`, `f1 = min(f0+1, F−1)`.

**Скорость и события:**
- `speed = 0` — пауза. Отрицательная скорость: loop заворачивается, one-shot упирается в кадр 0.
- One-shot заканчивается при `f ≥ F−1` (при отрицательной скорости — при `f ≤ 0`) и стоит на крайнем кадре.
- Событие «клип закончился» срабатывает один раз. Его считает CPU по той же формуле.

**Интерполяция:** 2 × `LOAD_TEXTURE2D_LOD` + lerp во float, без аппаратной фильтрации.

**Кватернионы:**
- выравнивание знака `q1 = dot(q0,q1) < 0 ? −q1 : q1`, не `sign()`: `sign(0)` обнуляет кватернион;
- нормализация `q·rsqrt(max(dot(q,q), 1e-8))`;
- nlerp. Slerp не нужен: при 24° за кадр разница меньше 0.1 мм, а стоит он дороже.

**Источник времени** — Time-нода SG, CPU-зеркало — `Time.time`.

### 1.4 Состояние юнита (3 × float4 в материале юнита)
```
_VatClipA = (±(startRow·4096 + F), rate, t0, offset)   // исходный клип; + loop, − one-shot
_VatClipB = (то же)                                    // целевой клип
_VatBlend = (wFrom, wTo, tStart, invDur)               // вес B: w(t) = lerp(wFrom, wTo, saturate((t−tStart)·invDur)), вес A = 1 − w
```
- **Упаковка клипа.** `startRow·4096 + F` лежит в [1, 2^24] (F ∈ [1, 4096], startRow < 4096): float32 хранит это точно, а ноль не встречается, так что знак loop/one-shot различим всегда. Декод: `p = (uint)abs(x) − 1; startRow = p >> 12; F = (p & 4095) + 1`.
- **Мгновенная смена** (длительность ≤ 0) — микро-рампа: началась 4 мс назад и длится 2 мс. В текущем кадре уже новое состояние, а при пересчёте прошлого кадра для motion vectors (dt ≥ 4.2 мс, до 240 fps) — ещё старое. Деления на ноль нет.
- **Постоянные ассета** (ширина текстуры, число строк, флаг дрейфа) лежат в `_VatLayout` (§1.9), их пишет бейкер в шаблон.
- Каждая запись проверяется на isfinite (assert).

### 1.5 Бленд и переходы
Сценарий один: клип переходит в другой клип.

**Шейдер.** Каждый клип считается целиком, `VatEval(clip) → (P, N, T)`, затем:
- `P = lerp(P_A, P_B, w)`;
- `n = lerp(N_A, N_B, w)`, `N = |n| > 1e-4 ? n/|n| :` нормаль доминирующего клипа (`w < 0.5 ? A : B`);
- `t = lerp(T_A, T_B, w) − N·dot(N, lerp(T_A, T_B, w))`, `T = |t| > 1e-4 ? t/|t| :` тангент доминирующего клипа, ортогонализованный к N.
- Динамические ветки: при w = 0 клип B не читается, при w = 1 — клип A.
- Блендятся готовые результаты, а не кости: бленд по костям рвёт суставы. Одна реализация на Vertex и Bone.

**Переходы (CPU, `VatAnimator`):**
- `CrossFade(clip, d)`: если предыдущий переход закончен (w = 1), целевой клип становится исходным (A := B, w = 0). Новый клип встаёт в B, его вес растёт 0 → 1 за d начиная с текущего момента.
- `Play(clip)` — это `CrossFade(clip, 0)`, то есть микро-рампа (§1.4).
- `SetWeight(w, T)`: вес перехода из кода — рампа от текущего значения до w за T (T = 0 — микро-рампа).
- `CrossFade` посреди незаконченного перехода по сценарию не используется, но поведение определено: доминирующий клип (вес ≥ 0.5) становится исходным, новый — целевым, третий выпадает с рывком. В редакторе и development-сборке — предупреждение в лог.
- Синхронизации фаз нет.

### 1.6 Материалы и батчинг
- **Копии материалов — только в Play mode и в сборке.** В edit mode `VatAnimator` материалы не трогает: превью идёт на шаблонном материале, клип по умолчанию выбирается в инспекторе `VatAsset` и пишется в свойства шаблона. Для движения в Scene view включается Always Refresh.
- **Копия на каждый уникальный VAT-шаблон.** В `OnEnable` `VatAnimator` собирает sharedMaterials всех своих рендереров, включая LOD, делает `new Material(template) { hideFlags = HideFlags.DontSave }` на каждый уникальный VAT-шаблон и ставит копии в слоты. Состояние пишется во все копии. Поле со списком копий — `[NonSerialized]`.
- **Уничтожение — в `OnDestroy`** (вызывается при `Destroy`, выгрузке сцены и выходе из Play mode). Пулинг через `SetActive` копии не пересоздаёт.
- **Экипировка** — отдельный меш, скиннённый на кости того же рига (например, 100% на кость руки), со своим VAT-материалом на той же bone-текстуре. Юнит пишет в него то же состояние.
- **Никогда `renderer.material`**: он сам клонирует материал, и копия утекает.
- **MaterialPropertyBlock запрещён.** Эффекты юнита (hit-flash, цвет команды, dissolve) пишутся через `VatAnimator.SetFloat/SetColor/SetVector` во все копии, сами копии доступны как `VatAnimator.Materials`. В редакторе и development-сборке `VatAnimator` при каждой записи состояния проверяет `renderer.HasPropertyBlock()` и пишет ошибку с именем объекта.
- **SRP Batcher.** Разные материалы с одним вариантом шейдера дешёвы, но это всё равно отдельный draw на рендерер в каждом проходе. Бюджет — по замеру в 1.14. «Enable GPU Instancing» на VAT-материалах выключен.
- **Варианты шейдера.** Каждый набор ключевых слов (Bone1, Bone2, Vertex, ключи теней) — отдельный батч. Валидатор показывает число разных вариантов VAT-материалов в сцене и предупреждает, если их больше порога.
- **Три свойства состояния — scope Hybrid Per Instance**, с «Promote to final Shader» в SubGraph. В обычных вариантах они попадают в `UnityPerMaterial` и совместимы с SRP Batcher, а путь DOTS нужен BRG-рендереру из патча 2 без переделки шейдеров.
- **Текстуры — Per Material**, Blackboard-свойства.
- **Запись только при изменении**: `SetVector` при командах. Повторно применять в `OnEnable`.
- **Не реализовывать `OnBecameVisible` и `OnWillRenderObject`**: они исключают объект из GRD, а он понадобится в патче 2.

### 1.7 Меш
Раскладка задаётся явно через `SetVertexBufferParams`, меш non-readable. Два потока (для IDVS на Mali): в потоке 0 позиция и кости, в потоке 1 всё остальное. Атрибуты по каналам — в карте §1.9.

Правила:
- **Выбор влияний:** два наибольших веса (при равенстве — меньший индекс кости), нормализация к сумме 1; вертекс без весов — 100% на корневую кость. Так же, как Unity при Skin Weights = 2, это сверяет тест против `BakeMesh`.
- **Никогда UInt или SInt на TexCoord**: через float4 в SG они приходят сырыми битами.
- **Кости — в TexCoord4.** Vertex Compression переводит UV2–UV7 в FP16 у non-readable Float32-каналов, и только в player-сборке, а UNorm-форматы не трогает. TexCoord4 заодно не пересекается с `uv2` динамических лайтмапов.
- **После бейка вершины не переставляются**: никаких `Mesh.Optimize`, `OptimizeReorderVertexBuffer` и сторонних оптимизаторов. Mesh LOD — только после проверки, что вершинный буфер не переставлен (1.18).

### 1.8 Ассеты
- **Формат — `.asset`**: главный объект `VatAsset` и sub-assets Mesh и Texture2D. На `VatAsset` стоит `[PreferBinarySerialization]` (проект в Force Text, без атрибута пиксели пишутся hex'ом).
- **Текстуры:** `new Texture2D(w, h, GraphicsFormat.R16G16B16A16_SFloat | R8G8B8A8_UNorm, TextureCreationFlags.None)` → `SetPixelData` → `Apply(false, true)` → `AddObjectToAsset`. Point, Clamp, без мипов. Конструктор с `TextureFormat` и `linear = false` даёт sRGB и портит байты — не использовать.
- **Повторный бейк — на тех же объектах:**
  1. новые Texture2D и Mesh собираются в памяти readable и целиком проверяются;
  2. `EditorUtility.CopySerialized(новый, существующий)` для каждого sub-asset'а;
  3. `m_IsReadable = false` через SerializedObject, затем `SaveAssets`.

  Пока шаг 1 не пройден, старый ассет не трогается. Так fileID и ссылки из материалов и префабов сохраняются даже при смене размеров (проверено на 6000.3).
- **Версия формата.** `VatAsset` хранит `formatVersion`, описание раскладки по §1.9 (строка пивотов, дрейф, число текселей на элемент, форматы) и хэш исходника и настроек бейка. Рантайм отказывается играть неподдерживаемую `formatVersion` с понятной ошибкой. Инспектор показывает «бейк устарел», если хэш исходника изменился.
- **Память в инспекторе:** фактические width×height×bytes каждой текстуры, padding, все клипы и LOD. Бюджет считается по уникальным ассетам.
- **Баунды** (`Mesh.bounds` и `SubMeshDescriptor.bounds`):
  - **Vertex:** объединение позиций по всем кадрам — между кадрами позиции интерполируются линейно и из оболочки не выходят;
  - **Bone и Rigid:** объединение капсул радиуса `s_max·ρ` вокруг отрезков, по которым между кадрами движутся пивоты (ρ — наибольшее расстояние вершины кости от пивота в bind-позе);
  - бленд клипов в объединение по клипам уже входит.

### 1.9 Карта каналов
Единственное место, где описано, что лежит в каждом канале. Остальные разделы ссылаются сюда.

**Текстуры.** Все — Point, Clamp, без мипов, linear. Адрес тексела — по §1.1: `x` — элемент, `row = b·totalRows + startRow + frame`.

| Текстура | Режим | Формат | Элемент x | R | G | B | A |
|---|---|---|---|---|---|---|---|
| `_VatPosTex` | Vertex | RGBAHalf | вертекс | Δ.x | Δ.y | Δ.z | 0 |
| `_VatRotTex` | Vertex | RGBA8 | вертекс | байт a | байт b | байт c | старшие биты и индекс (ниже) |
| `_VatDriftTex` | Vertex с дрейфом | RGBAHalf | 0 — hi, 1 — lo | d.x | d.y | d.z | 0 |
| `_VatBoneTex`, строка 0 | Bone, Rigid | RGBAHalf | 2i | p̃.x | p̃.y | p̃.z | 0 |
| `_VatBoneTex`, строка 0 | Bone, Rigid | RGBAHalf | 2i + 1 | 0 | 0 | 0 | 0 |
| `_VatBoneTex`, кадры | Bone, Rigid | RGBAHalf | 2i | Δ.x | Δ.y | Δ.z | s |
| `_VatBoneTex`, кадры | Bone, Rigid | RGBAHalf | 2i + 1 | q.x | q.y | q.z | q.w |

- **Vertex:** `Δ = pos − rest − d` (без дрейфа `d = 0`). Строки — только кадры: `totalRows = ΣF`, первый клип с `startRow = 0`.
- **Дрейф:** `_VatDriftTex` без блоков — ширина 2, высота ΣF, строка `startRow + frame`. `d = hi + lo`, в шейдере `pos = rest + lerp(d0, d1) + lerp(Δ0, Δ1)`.
- **Bone и Rigid:** `i` — индекс кости или куска, элементов `E = 2·N`. Строка 0 каждого блока — пивоты, `totalRows = 1 + ΣF`, клипы начинаются со `startRow = 1`. `p̃` — пивот, округлённый до half; `Δ = p_pose − p̃`; `s` — равномерный масштаб, `s = 0` — кусок скрыт.
- **Кватернион** — (x, y, z, w), w — скалярная часть. В Vertex он задаёт кадр (T, N×T, N): `N = rot(q, (0,0,1))`, `T = rot(q, (1,0,0))`, знак бинормали — `tangent.w` меша.
- **`_VatRotTex`, smallest-three:**
  - `idx` — индекс наибольшей по модулю компоненты (0..3); если она отрицательна, весь q умножается на −1; сама компонента не хранится;
  - a, b, c — три оставшиеся компоненты по порядку x, y, z, w, пропуская idx;
  - каждая — 10 бит: `n = round((c·√2·0.5 + 0.5)·1023)`;
  - `R = n_a & 255`, `G = n_b & 255`, `B = n_c & 255`, `A = idx<<6 | (n_c>>8)<<4 | (n_b>>8)<<2 | (n_a>>8)`;
  - декод: байты = `round(v·255)`; `n_a = R | (A & 3)<<8`, `n_b = G | ((A>>2) & 3)<<8`, `n_c = B | ((A>>4) & 3)<<8`, `idx = A >> 6`; компонента `= (n/1023·2 − 1)/√2`; пропущенная `= sqrt(saturate(1 − a² − b² − c²))` встаёт на место idx.

**Меш**

| Поток | Атрибут | Формат | Содержимое |
|---|---|---|---|
| 0 | Position | Float32×3 | позиция покоя: rest в Vertex, bind-поза в Bone, исходная в Rigid |
| 0 | TexCoord4 | UNorm8×4 (`_VAT_BONES_2`) | `(i0/255, i1/255, w_hi/255, w_lo/255)` |
| 0 | TexCoord4 | UNorm16×2 (`_VAT_BONES_1`, Rigid) | `(i/65535, 0)` |
| 1 | Normal | Float16×4 | нормаль покоя, w = 0 |
| 1 | Tangent | Float16×4 | тангент покоя, w = знак бинормали ±1 |
| 1 | TexCoord0 | Float16×2 | UV |

- **Вес:** `w0 = (round(z·255)·256 + round(w·255)) / 65535`, `w1 = 1 − w0`.
- **Индексы:** `i = (uint)round(uv.x·255)` и `(uint)round(uv.y·255)` для UNorm8; `i = (uint)round(uv.x·65535)` для UNorm16. Bone2 — до 256 костей, Bone1 и Rigid — до 2048.
- **В Vertex-режиме TexCoord4 нет.**
- **Vertex color** (UNorm8×4) и дополнительные UV (Float16×2) переносятся в поток 1, только если включены в профиле бейка.

**Материал**

| Свойство | Scope | Содержимое |
|---|---|---|
| `_VatClipA`, `_VatClipB` | Hybrid Per Instance | `(±(startRow·4096 + F), rate, t0, offset)` — §1.4 |
| `_VatBlend` | Hybrid Per Instance | `(wFrom, wTo, tStart, invDur)` — §1.4 |
| `_VatLayout` | Per Material | `(W, totalRows, driftOn, 0)` — постоянные ассета, бейкер пишет их в шаблон |
| `_VatPosTex`, `_VatRotTex`, `_VatDriftTex`, `_VatBoneTex` | Per Material | текстуры ассета |

## 2. Режимы

### 2.1 Bone — персонажи из SMR (этап В, подверсии 1.11–1.14)

**Данные** (каналы — §1.9):
- **`_VatBoneTex`:** строка 0 — пивоты `p̃_bind` (уже округлённые до half); в строках кадров на кость 2 тексела: `(Δ.xyz, s)` и `q`, где `Δ = p_pose − p̃_bind` — смещение сустава от позы покоя.
- **Меш:** bind-поза в Position, индексы и веса в TexCoord4.
- **Память:** 16 Б на кость-кадр.

**Скиннинг:** `v' = Σ wᵢ·(sᵢ·rot(qᵢ, v − p̃_bindᵢ) + p̃_bindᵢ + Δᵢ)`. Между кадрами lerp Δ и s, nlerp q. N и T так же, но без трансляции, потом normalize.

**Разложение skin-матрицы:**
- `M = root⁻¹ · L2W · bindpose · A⁻¹` (A фиксирован на старте бейка), B — линейная часть M;
- `det B ≤ 0` (отражение или вырождение) — клип уходит в Vertex-режим или бейк падает с сообщением;
- `s = cbrt(det B)`, R — полярное разложение B;
- **равномерный масштаб:** остаток `‖B − sR‖/s ≤ 1e-3` и ошибка `‖(B − sR)(v − p_bind)‖` на вершинах кости не больше 0.5 мм, иначе клип уходит в Vertex. Ортогональность самого R не проверять: у полярного разложения она есть всегда;
- `p_bind` — только из bindposes;
- `p_pose = M·p̃_bind` считается от уже округлённого пивота, `Δ = p_pose − p̃_bind`.

**Бюджеты ошибки:** на кадрах бейка — меньше 1 мм, включая квантование Δ, q и весов. Между кадрами ошибка интерполяции больше (до ~1 см на быстрых клипах при 30 fps), её оценивает предупреждение о FPS (§2.3).

**Influences:**
- на мобилках максимум 2 (уровень Mobile в проекте уже использует `skinWeights: 2`);
- ключи `_VAT_BONES_1` и `_VAT_BONES_2`; 1 influence — ещё и для дальних LOD;
- `_VAT_BONES_4` — только desktop: на Mali 4 influences спиллят регистры. На мобильных сборках вырезается.

**Бейкер `SkinnedFrameSource`:**
- **Копия для бейка, один раз перед всеми клипами:** `animator.enabled = true`, `runtimeAnimatorController = null`, `AnimatorUtility.DeoptimizeTransformHierarchy`.
- **Перед каждым клипом — сброс:** все трансформы из снимка позы по умолчанию и веса блендшейпов, иначе результат зависит от порядка клипов.
- **Generic и Humanoid:** PlayableGraph, `applyRootMotion = false`, `SetApplyFootIK(false)` явно (у нового playable foot IK включён):
  ```csharp
  var g = PlayableGraph.Create("VatBake");
  g.SetTimeUpdateMode(DirectorUpdateMode.Manual);
  var output = AnimationPlayableOutput.Create(g, "out", animator);
  var cp = AnimationClipPlayable.Create(g, clip);
  cp.SetApplyFootIK(false);
  output.SetSourcePlayable(cp);
  try {
      for (int k = 0; k < F; k++) {
          cp.SetTime(k / fpsEff);
          g.Evaluate();
          // снять позы костей
      }
  } finally { g.Destroy(); }
  ```
  `g.Play()` и прогрев `Evaluate(0)` не нужны.
- **Legacy-клипы:** `clip.SampleAnimation`.
- **Root motion.** VAT-анимация всегда на месте, двигает юнита геймплей. Второй проход с `applyRootMotion = true` пишет в `VatClip` `averageSpeed`. `VatAnimator` подгоняет скорость проигрывания под скорость движения (`speed = v / averageSpeed`, во время перехода — средняя по весу).
- **Перевод в пространство корня префаба** (FBX: −90° по X и скейл 0.01).

### 2.2 Vertex — деформации, ткань, жидкости с постоянной топологией (этап А, подверсии 1.1–1.5)

**Данные** (каналы — §1.9):
- **`_VatPosTex` RGBAHalf:** offset от rest, где rest = вершины меша = первый кадр.
- **`_VatRotTex` RGBA8:** кватернион кадра (T, N×T, N) в smallest-three 2+10+10+10 сырыми байтами. После декода — выравнивание знака и nlerp между кадрами.
- **Дрейф.** Бейкер сам включает его (`driftOn` в `_VatLayout`), если центроид клипа уходит дальше ~2 м или прогноз ошибки half больше 1 мм. Смещение кадра хранится парой hi/lo в `_VatDriftTex`.
- **Память:** 12 Б на вертекс-кадр, дрейф — ещё 16 Б на кадр.

**Тангенты и нормали:**
- тангенты пересчитываются на каждый кадр; перед построением кватерниона T ортогонализуется к N (Грам–Шмидт), `B = N × T`;
- знак бинормали — статичный из `tangent.w`; несовпадения хиральности бейкер сообщает;
- при вырожденных UV тангент переносится с прошлого кадра: `T_k = normalize(T_{k−1} − N_k·dot(N_k, T_{k−1}))`, в кадре 0 — детерминированный базис от N;
- после `BakeMesh` нормали нормализуются.

**Источники:**
- **SMR → Vertex:** `BakeMesh`, включая блендшейпы. Cloth `BakeMesh` не видит: ткань пишется Alembic Recorder'ом в Play mode, дальше Alembic → Vertex.
- **Alembic, только постоянная топология.** Проверки по всем кадрам: число вертексов, хэш индексов, хэш UV, разбиение на сабмеши. Плюс предупреждение, если вертекс сдвинулся за кадр больше чем на половину баунда меша. Контракт экспорта: стабильный порядок точек, без перестроения сетки. Проверки не прошли — ошибка «меняющаяся топология — патч 2».
- **Жидкости с постоянной топологией** идут сюда же. Без UV материал триплэнарный.
- **Автоопределение петли** — только подсказка в инспекторе, решает пользователь.

### 2.3 Rigid — разрушения из Alembic (этап Г, подверсии 1.15–1.16)

**Данные** (каналы — §1.9):
- **Bone-режим с 1 influence** (`_VAT_BONES_1`): тот же формат, тот же SubGraph `VAT_Bone`, кусок = кость.
- **Меш:** вершины в исходных позициях в Position, индекс куска в TexCoord4 (UNorm16).
- **`_VatBoneTex`:** строка 0 — пивоты кусков `p̃` (см. ниже, округлённые до half); в строках кадров — `(Δ, s)` и `q`, где Δ — смещение пивота от покоя.
- **Память:** 16 Б на кусок-кадр.

**Пивот** — точка минимального ускорения методом наименьших квадратов (одно решение 3×3):
`c* = −(Σ AᵀA)⁻¹ Σ Aᵀb`, где `A = R_{f+1} − 2R_f + R_{f−1}`, `b = t_{f+1} − 2t_f + t_{f−1}`. При плохой обусловленности — центр баунда.

**Куски:**
- **Из xform-нод.** Рецепт экспорта: Houdini Packed Transform = Transform Geometry, `s@path` + Build Hierarchy From Attribute.
- **Fallback, если xform-нод нет** (экспорт Deform Geometry, возможно дефолтный в Houdini **[проверить]**):
  - острова по связности индексов, без сварки по позиции;
  - на каждый кадр подгонка Kabsch/Horn к кадру 0;
  - острова с совпадающими (R, t) на всех кадрах сливаются в один кусок (швы UV и жёстких нормалей режут кусок на острова);
  - критерий куска — максимальная невязка по вершинам и кадрам ≤ 0.5 мм;
  - если хоть один остров не прошёл, бейк падает с отчётом: какие острова и какая невязка.

**Видимость:**
- `s = 0` переключается ступенькой, без lerp;
- `q` и `Δ` берутся от последнего видимого кадра, кадры до первого появления — из первого видимого; кусок, который не появляется ни разу, выбрасывается;
- `q = 0` не писать никогда;
- `N' = normalize(Σ wsRn + 1e-6·n)`.

**Alembic 2.4.5:**
- кадр k семплится вызовом `UpdateImmediately(k / fps)`: аргумент отсчитывается от `StartTime` и зажимается в [0, Duration]. Абсолютное время файла передавать нельзя;
- `frameCount = round(Duration·fps) + 1`; `Duration ≤ 0` или нет мешей — ошибка бейка;
- перед сэмплингом корень плеера ставится в identity;
- вырезать `.abc` из мобильного билда пакет Alembic умеет сам.

**Предупреждение о FPS бейка** — оценка ошибки реконструкции между кадрами бейка: для SMR три внутренние точки на интервал, для Alembic — все отсчёты исходника между кадрами бейка. Порог: 2 мм для персонажей, 5 мм для обломков.

## 3. Motion vectors и проходы
- В примерах явно ставится **Additional Motion Vectors = Time Based**, иначе MV от VAT нулевые.
- URP пересчитывает вершины с прошлым временем при текущем состоянии материала. Любая смена состояния — рампа, начатая в текущий момент (§1.5), мгновенная — микро-рампа (§1.4). Поэтому MV правильные для Play, CrossFade, SetWeight и спавна из пула.
- Когда TAA или motion blur включены, MV-проход удваивает цену VAT.
- Прозрачные VAT-материалы MV не пишут (ограничение URP).
- Вертексный шейдер выполняется в каждом проходе: forward, каждый каскад теней, depth prepass, MV. Шейдер тени использует нормаль для normal bias, тангент ему не нужен. На Adreno может добавиться binning-проход **[проверить]**.

## 5. Патч 1 — порядок работ по подверсиям

**Как пользоваться.** Исполнителю даётся весь план и номер подверсии: «Реализуй подверсию 1.N, следующие не трогай». Разделы §0–§4 — справочник, этот раздел — порядок работ. Подверсия принимается по чек-листу «Как проверить», и только после этого начинается следующая.

**Принципы:**
- **Каждая подверсия — законченный шаг**, который собирается и проверяется отдельно. Первая — минимально возможная: только Vertex-запечка позиций.
- **Форматы данных и состояние сразу финальные** (§1), поэтому ранние подверсии потом не переделываются, а только дополняются.
- **Проверки на устройствах — внутри тех подверсий, где появляется риск.** Устройства: iPhone 12 (Metal), Android Adreno 650-класса и Mali-G78-класса (Vulkan и GLES 3.1). Всегда в player-сборке IL2CPP: сжатие меша, стрип и точность сэмплера в редакторе не видны.
- **Сцена Compare** появляется в 1.1 и растёт с каждой подверсией: исходник и VAT бок о бок.
- **Версии Unity:** пакет проверяется на 6000.3 (минимум) и на версии проекта (6000.5).

**Тестовый контент — подготовить заранее:**

| Для подверсий | Что нужно |
|---|---|
| 1.1–1.3, 1.6–1.10 | Персонаж со SkinnedMeshRenderer больше 2048 вертексов, 3–5 клипов (loop и one-shot), normal map; отдельно меш больше 4096 вертексов |
| 1.4–1.5 | Alembic с постоянной топологией: ткань или soft body; soft body, который перемещается на 20+ м; по желанию — жидкость с постоянной топологией без UV |
| 1.11–1.14 | Персонаж для толпы (не больше 2 influences на вертекс), 3–5 клипов; его LOD-меши; оружие для руки |
| 1.15 | Разрушение из Houdini, экспорт Transform Geometry + `@path` |
| 1.16 | То же разрушение, экспорт Deform Geometry |

### Этап А — Vertex-запечка

#### 1.1 Минимальная версия: позиции, один клип, ближайший кадр
**Цель:** пройти весь путь «бейк → ассет → шейдер → телефон» на самом простом случае.

**Входит:**
- пакет и asmdef: Runtime, Editor, Tests (§4);
- `VatBakeProfile` с минимумом полей: префаб со SMR, один клип, fps;
- `SkinnedFrameSource`: копия для бейка, PlayableGraph с выключенными foot IK и root motion, `BakeMesh`, перевод в пространство корня префаба (§2.1). Анимация блендшейпов, если она есть в клипе, запекается сама через `BakeMesh`;
- `VertexEncoder`, только позиции: `_VatPosTex` RGBAHalf, offset от rest (§1.9, §2.2);
- меш с финальной раскладкой (§1.7), baseVertex = 0, баунды — объединение всех кадров (§1.8);
- `VatAssetWriter`: `.asset` с `[PreferBinarySerialization]`, повторный бейк на месте через `CopySerialized`, `formatVersion` (§1.8);
- `VatCore.hlsl`: адресация (§1.1), упаковка клипа (§1.4), индекс кадра loop с клампом (§1.3), без интерполяции;
- `VatShaderGraph.hlsl` с обёртками `_float`, SubGraph `VAT_Vertex` с Precision Single, только позиция;
- пример Unlit и материал-шаблон, в который бейкер пишет клип;
- сцена Compare: SMR и VAT рядом.

**Не входит:** интерполяция, нормали из анимации (свет идёт по нормалям покоя), несколько клипов, VatAnimator, переходы, Alembic, Bone.

**Как проверить:**
- в Compare VAT совпадает с SMR на кадрах бейка: при пошаговом проигрывании кадр в кадр;
- повторный бейк с другим fps: материал и префаб не теряют ссылки, в том числе после перезапуска редактора;
- на трёх устройствах, в Metal, Vulkan и GLES: персонаж анимируется и совпадает по форме с редактором, объект не Static.

**Тесты:** адресация и блоки ширины; упаковка клипа, включая startRow = 0 и F = 1; кламп кадра на f ∈ {−1e-7, −kF, kF ± ulp}; раскладка меша совпадает с `VatLayout` (`GetVertexAttributes`, `GetVertexBufferStride`, round-trip вертексов, пока меш readable); бейк → перезагрузка → байты текстуры те же; повторный бейк сохраняет fileID; Half-родитель вызывает `_float`.

**Риски, которые закрывает:** Vertex ID и baseVertex на всех API, точность half через Shader Graph, формат меша и данные ассета в player-сборке.

#### 1.2 Плавность: интерполяция кадров и правила времени
**Входит:**
- 2 выборки + lerp (§1.3);
- раскладка loop и one-shot, флаг loop в упаковке клипа;
- якорь времени, speed, пауза, отрицательная скорость. Управление пока через свойства материала.

**Как проверить:** бейк на 10 fps выглядит плавно; шов loop без рывка; one-shot останавливается на последнем кадре; speed 0.5, 2 и −1 из инспектора материала.

**Тесты:** формулы времени и клампа на CPU: F ∈ {1, 2}, короткий loop (L·fps < 0.5), нулевая и отрицательная скорость, t = 4 ч.

#### 1.3 Свет: нормали и тангенты
**Входит:**
- `_VatRotTex` RGBA8 со smallest-three (§1.9, §2.2);
- тангенты по кадрам, Грам–Шмидт, перенос тангента при вырожденных UV, нормализация после `BakeMesh`, предупреждение о хиральности;
- пример Lit с normal map.

**Как проверить:** свет, блики и normal map совпадают с SMR; нет щелей на UV-швах; на трёх устройствах байты RGBA8 декодируются точно (тестовая текстура с известными значениями).

**Тесты:** кодек smallest-three на всех индексах и граничных компонентах; перенос тангента детерминирован.

#### 1.4 Alembic → Vertex (постоянная топология)
**Входит:**
- asmdef `VATyakov.Editor.Alembic` с defineConstraints (§4);
- `AlembicFrameSource`: `UpdateImmediately(k / fps)`, корень плеера в identity, frameCount (§2.3);
- проверки топологии и соответствия вершин (§2.2), подсказка периода loop;
- пример `VAT_Lit_Vertex_Triplanar` для мешей без UV.

**Как проверить:** ткань или soft body из .abc выглядит так же, как в AlembicStreamPlayer; .abc с меняющейся топологией даёт понятную ошибку; пакет без установленного Alembic компилируется.

**Тесты:** VAT против кадров Alembic — ошибка в пределах квантования; переставленные вершины дают предупреждение; `Duration ≤ 0` — ошибка бейка.

#### 1.5 Дрейф для перемещающихся тел
**Входит:** `_VatDriftTex` с парой hi/lo half и автовключение по порогу (§1.9, §2.2).

**Как проверить:** soft body, который улетает на 20+ м, не дрожит; инспектор показывает ошибку с дрейфом и без.

**Тесты:** кодек дрейфа.

### Этап Б — рантайм, общий для всех режимов

#### 1.6 Несколько клипов в одном ассете
**Входит:**
- таблица клипов, клипы друг под другом в текстуре, лимит высоты 4096 с ошибкой бейка (§1.1);
- сброс позы и блендшейпов перед каждым клипом (§2.1);
- клип по умолчанию для превью выбирается в инспекторе `VatAsset` и пишется в шаблон (§1.6).

**Как проверить:** все клипы играют, переключение через инспектор материала; меш больше 4096 вертексов уходит в блоки и играет верно; превью в Scene view с включённым Always Refresh.

**Тесты:** бейк клипов в двух порядках даёт одинаковый результат; переполнение высоты — понятная ошибка.

#### 1.7 VatAnimator: материал на юнита и управление
**Входит:**
- копии материалов только в Play mode, по одной на уникальный VAT-шаблон, уничтожение в `OnDestroy` (§1.6);
- `Play`, `Speed`, `Pause/Resume`, `GetNormalizedTime`, событие «клип закончился», `playOnEnable`;
- `SetFloat/SetColor/SetVector` и `Materials` для эффектов юнита;
- dev-проверка `HasPropertyBlock()`.

**Как проверить:**
- смена клипа из скрипта, событие «клип закончился» срабатывает один раз;
- пул юнитов через `SetActive`: число материалов в Memory Profiler не растёт;
- сохранение сцены в edit mode не портит материалы;
- hit-flash через `SetColor`;
- на устройстве кадр, который считает CPU, совпадает с кадром в шейдере.

**Тесты:** CPU-зеркало кадра совпадает с формулой шейдера; события one-shot при положительной и отрицательной скорости.

#### 1.8 Переходы: CrossFade и вес из кода
**Входит:**
- `_VatClipB` и `_VatBlend`, бленд двух клипов в шейдере с fallback'ами нормали и тангента (§1.5);
- `CrossFade(clip, d)`, `SetWeight(w, T)`, `Play` через микро-рампу (§1.4);
- поведение при `CrossFade` посреди перехода и предупреждение в лог.

**Как проверить:** переходы плавные, без рывков; переходом можно управлять из скрипта через `SetWeight`; `CrossFade` посреди перехода пишет предупреждение.

**Тесты:** веса и рампы на CPU; микро-рампа; `d ≤ 0` без NaN; противоположные N и T при весе 0.5 без NaN.

#### 1.9 Motion vectors
Нужна, если в проекте включат TAA или motion blur, до этого её можно отложить.

**Входит:** Additional Motion Vectors = Time Based в примерах (§3), визуализация MV в Compare.

**Как проверить:** MV без выбросов после Play, CrossFade, SetWeight и спавна из пула; на устройстве с TAA нет шлейфов.

**Тесты:** MV-контракт на CPU: поза прошлого кадра при новом состоянии совпадает с позой при старом — после Play, CrossFade, Pause и Speed.

#### 1.10 Инструменты и защита сборки
**Входит:**
- инспектор `VatAsset`: память (width×height×bytes, padding), максимальная ошибка в мм с учётом fp16, «бейк устарел» по хэшу исходника (§1.8);
- `VatBuildValidator`:
  - **область:** сцены из Build Settings и все ассеты, которые зависят от VAT-мешей (префабы, Addressables, Resources), плюс URP-ассеты всех уровней Quality;
  - каждый слот материала у рендерера с VAT-мешем — VAT-материал;
  - `baseVertex == 0`;
  - нет Batching Static;
  - dynamic batching выключен во всех URP-ассетах;
  - нет fp32 VAT-текстур;
  - число разных вариантов VAT-материалов — предупреждение выше порога.

**Как проверить:** сборка с каждым нарушением (Static-объект, fp32-текстура, не-VAT материал на VAT-меше) падает с понятным сообщением; цифры памяти в инспекторе совпадают с Memory Profiler.

**Тесты:** на каждое правило валидатора — фикстура с нарушением.

### Этап В — Bone, персонажи для толпы

#### 1.11 Bone с одной костью на вертекс
**Входит:**
- `BoneEncoder` (§2.1): `_VatBoneTex` — строка пивотов, (Δ, s) и q (§1.9);
- разложение skin-матрицы с проверками: `det B ≤ 0`, остаток `‖B − sR‖` и ошибка в мм;
- индекс кости в TexCoord4 UNorm16 (§1.9), SubGraph `VAT_Bone` с `_VAT_BONES_1`;
- нормали и тангенты поворотом кости, баунды-капсулы (§1.8).

**Как проверить:** персонаж совпадает с SMR при Skin Weights = 1 Bone; клипы, VatAnimator и переходы работают без изменений (общее ядро); клип с неравномерным масштабом кости уходит в Vertex с сообщением.

**Тесты:** skin-матрица `diag(2, 1, 0.5)` уходит в Vertex; капсула содержит дугу при повороте от −30° до +90° за кадр; реконструкция против `BakeMesh` при `smr.quality = 1`.

#### 1.12 Bone с двумя influences
**Входит:** TexCoord4 UNorm8×4 с 16-битным весом (§1.9), выбор двух наибольших весов, нормализация (§1.7); `_VAT_BONES_2`.

**Как проверить:** совпадение с SMR при Skin Weights = 2 Bones; на трёх устройствах веса декодируются точно.

**Тесты:** против `BakeMesh` при `smr.quality = 2` по упакованному мешу — меньше 1 мм, в том числе при весе 0.5 и большом рычаге; при равных весах побеждает меньший индекс кости.

#### 1.13 Bone в игре: LOD, экипировка, скорость
**Входит:**
- LOD-меши одного рига на общей bone-текстуре; bindposes проверяются на равенство;
- экипировка — меш, скиннённый на кость руки, со своим VAT-материалом (§1.6);
- `averageSpeed` и подгонка скорости проигрывания под скорость движения (§2.1).

**Как проверить:** LOD переключаются без скачка позы; оружие в руке не отстаёт; юнит идёт с заданной скоростью без скольжения ног.

#### 1.14 Приёмка толпы
**Входит:**
- сцена Stress: 100 юнитов со случайными клипами и переходами против 100 SMR с Mesh Deformation = GPU (Batched). Худший случай: все 100 юнитов делают `CrossFade` каждый кадр;
- **протокол замера:**
  - IL2CPP Release, прогрев, затем 10 минут;
  - в отчёт записывается конфигурация: разрешение, вершин на юнит, число видимых юнитов, доля юнитов в переходе, свет, дальность и число каскадов теней, MSAA, TAA, SSAO, версии Unity и URP;
  - замеры: CPU main и render thread, GPU кадр и по проходам, аллокации, память;
  - сравнение с SMR при том же качестве и тех же 2 influences;
  - «CPU на анимацию» означает: нет работы на юнит в кадр, остаются только события — команды и завершения клипов.

**Как проверить:** отчёт по протоколу на трёх устройствах; Frame Debugger показывает SRP Batch во всех проходах. По результатам фиксируются критерий выигрыша (насколько VAT дешевле SMR) и бюджеты: вершин на юнит, каскадов, influences.

### Этап Г — Rigid, разрушения

#### 1.15 Rigid из Alembic с xform-нодами
**Входит:**
- `RigidPieceExtractor`: куски из xform-нод становятся костями Bone1 (§2.3);
- LS-пивот, смещения от покоя;
- видимость: ступенька, заполнение кадров до первого появления, выброс кусков, которые не появляются;
- предупреждение о FPS по внутренним отсчётам;
- рецепт экспорта из Houdini в документации.

**Как проверить:** разрушение совпадает с AlembicStreamPlayer; в покое между кусками нет щелей; куски появляются и исчезают вовремя; 500 кусков × 150 кадров ≈ 1.2 MB.

**Тесты:** кусок, невидимый с кадра 0; LS-пивот на синтетике; быстрое вращение вызывает предупреждение о FPS.

#### 1.16 Rigid без xform-нод
**Входит:** острова по связности, подгонка Kabsch, слияние островов с совпадающими (R, t), критерий — максимальная невязка ≤ 0.5 мм, отчёт об ошибке (§2.3).

**Как проверить:** экспорт Deform Geometry даёт тот же результат, что и Transform Geometry; экспорт с деформирующимися кусками даёт отчёт со списком островов.

**Тесты:** острова, разрезанные швами, сливаются; деформирующийся остров — ошибка с отчётом.

### Этап Д — оптимизация

#### 1.17 Тени
**Входит:** opt-in ключи `_VAT_SHADOW_DOMINANT` и `_VAT_SHADOW_1INFL` через проверку `SHADERPASS == SHADERPASS_SHADOWCASTER` в Custom Function; рекомендация по прокси для теней — низкополигональный меш с ShadowsOnly (§3).
- `_VAT_SHADOW_DOMINANT` — во время перехода тень только от клипа с большим текущим весом: `w(t) ≥ 0.5 ? B : A`. Когда вес проходит 0.5, поза тени переключается за один кадр, поэтому ключ opt-in.

**Как проверить:** замер прохода тени на устройствах до и после; тень без заметных артефактов.

#### 1.18 LOD через Mesh LOD
**Входит:** генерация Mesh LOD для .asset-мешей с проверкой, что вершины не переставлены (§1.7). Если это не работает — LODGroup с отдельными мешами на общей текстуре.

**Как проверить:** LOD переключаются, анимация совпадает на всех уровнях.

#### 1.19 Финальные бюджеты
**Входит:** профилирование на устройствах (Xcode GPU counters, Snapdragon Profiler в режиме binning или direct, Arm Streamline) и сверка с Mali Offline Compiler; документ с бюджетами для художников.

**Как проверить:** документ с цифрами по каждому режиму и устройству.

## 6. Патч 2 — в планах
1. **Жидкости с меняющейся топологией** — mesh sequence: меш на кадр и переключение `sharedMesh`. Выглядит так же, как развёрнутый VAT, но памяти примерно в 3 раза меньше и вертексной работы в 6 раз меньше. Развёрнутый VAT — только для десятков одинаковых копий одной симуляции.
2. **Толпы больше ~100** — BRG-рендерер (шейдеры уже готовы через Hybrid Per Instance) или `SetShaderUserValue` + GPU Resident Drawer на Vulkan и Metal с Forward+. MPB не используется и здесь.
3. **Бленд, если сценарий расширится:**
   - долгая смесь двух циклов с синхронизацией фаз (например, walk/run по скорости): темп меняется линейно по рампе веса, фаза квадратична, +1 float4;
   - бесшовное прерывание незаконченного перехода — больше двух клипов в состоянии;
   - compute-проход с локальным блендом и FK.
4. **Форматы:** Vertex 8 Б (RGBA8 11:11:10 по баунду клипа) для фона и LOD; 16 бит по баунду для больших не-rigid симуляций.
5. **LOD:** префиксный LOD для Vertex, если Mesh LOD (1.18) не заработает; ключ «без интерполяции» — только если замеры на Adreno или Bifrost покажут выигрыш.
6. **Rigid:** интерполяция с учётом скорости для очень быстрых кусков; смешанный результат rigid + vertex для островов, не прошедших подгонку.
7. **Root motion по кривой** вместо `averageSpeed`.

## 7. Подводные камни
- Только RGBAHalf и RGBA8; fp32, RGBA16 UNORM, сжатие, мипы и sRGB у VAT-текстур запрещены.
- VAT-SubGraph и Custom Function всегда Precision Single.
- baseVertex = 0; никакого static или dynamic batching и объединённых мешей.
- Высота VAT-текстуры ≤ 4096 без исключений.
- После бейка вершины не переставляются.
- `renderer.material` не трогать; копии материалов — только в Play mode, `DontSave`, уничтожение в `OnDestroy`.
- MaterialPropertyBlock запрещён; эффекты юнита пишутся в его материалы через `VatAnimator`.
- У нового playable foot IK включён — выключать явно. Перед каждым клипом сбрасывать позу и блендшейпы.
- В кватернионах `sign()` не использовать; `q = 0` не писать.
- Повторный бейк — только через `CopySerialized` в существующие sub-assets.

**Не использовать** (проверено, не подходит):
- бленд по костям — рвёт суставы; DLB — не проходит бюджет качества;
- slerp — не нужен;
- `Texture2D.Reinitialize` при повторном бейке — бросает исключение на non-readable текстуре;
- RGB10A2 — не создаётся как Texture2D;
- `AnimationMode` для бейка — оставляет root motion в позе;
- UInt/SInt вертексные форматы, UV-каналы под адресацию, SSBO в вертексном шейдере.
