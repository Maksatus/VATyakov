## 1. Общее ядро

### 1.1 Адресация
- **X = элемент** (вертекс или тексел кости), **Y = кадр**. Все клипы ассета лежат в одной текстуре друг под другом, без padding-строк, в порядке списка Clips профиля. Loop и fps — общие для всех клипов профиля (1.6). Имена клипов в ассете уникальны (проверка бейка): по имени клип ищут `VatAnimator` и перебейк шаблона (§1.6). **E** — число элементов, **F** — число кадров клипа.
- **Индекс — из Vertex ID** (нода SG), не из UV.
- **Ширина не степень двойки:** `W = ceil(E / ceil(E / 4096))`. В шейдере `uint b = id / W; uint x = id − b·W; y = b·totalRows + row`, `row` приходит с CPU (§1.4).
- **Высота ≤ 4096 без исключений.** Если `blocks·totalRows > 4096`, бейк падает с сообщением: уменьшить fps или длину клипов либо разнести клипы по разным `VatAsset`. Кроссфейд возможен только внутри одного ассета.
- **baseVertex = 0 на всех сабмешах.** D3D и Metal исключают его из SV_VertexID, Vulkan и GLES включают. Поэтому запрещены static batching, dynamic batching и объединённые меши.

### 1.2 Точность
- **Текстуры с Blackboard** Shader Graph на мобилках читаются через mediump-сэмплер (Shader Precision Model = Platform Default, как в проекте). Поэтому VAT-текстуры — **только RGBAHalf и RGBA8**. fp32 точности не добавляет и стоит дороже, бейкер его не пишет.
- **RGBA8 — линейное число, не байты** (1.8.2): кватернион декодируется одним `mad`, побитной упаковки нет. Ошибка
  mediump-выборки (до 2⁻¹¹ от значения) меньше шага квантования 1/127, точность байтов на устройствах проверять не нужно.
- **Позиции хранятся смещениями от покоя:** в Vertex — от rest-меша, в Bone и Rigid — от позы покоя кости. Ошибка half тогда пропорциональна смещению, а не расстоянию до origin.
- **Vertex: half или 8 бит** (1.8.3). Смещение без дрейфа кладётся либо в RGBAHalf, либо байтом на ось в RGBA8 внутри
  габаритов смещений ассета (min, size по осям). Бейкер считает максимальную ошибку 8 бит с учётом fp16-выборки и печёт
  8 бит, если она меньше Max Position Error профиля (по умолчанию 8 мм; 0 — всегда half). Ошибка 8 бит ≈ размах
  деформации по оси / 510; дрейф (перенос тела) в размах не входит. 8 бит вдвое уменьшают текстуру позиций.
- **Дрейф d — float32 на CPU:** массив строк в `VatAsset`, в шейдер приходит готовым вектором `_VatDrift` (§1.4). Пары hi/lo half и `_VatDriftTex` нет с 1.8.1.
- **VAT-SubGraph и все Custom Function — Precision Single**, обёртки только `_float`. Иначе Vertex ID станет half и сломается выше 2048.
- **Инспектор показывает ошибку с учётом fp16-выборки**, а не точность хранения.

### 1.3 Индекс кадра и время

**Раскладка клипа:**
- **Loop:** `F = max(1, round(L·fps))`, `t_k = k·L/F`, `fps_eff = F/L`. Последний кадр не дублирует первый.
- **One-shot:** `F = round(L·fps) + 1`, `fps_eff = (F−1)/L`.
- `L ≤ 0`, `fps ≤ 0` или нечисловые значения — ошибка бейка.

**Всё ниже считает CPU** (`VatPlayback`, `VatClip.Frame`), в double. Шейдер времени не знает (§1.4).

**Время:** `f = (t − t0)·fps_eff·speed + offset`, `t` — `Time.timeAsDouble`.
- **Loop:** `offset` держится в [0, F).
- **One-shot:** `offset` в [0, F−1] без заворота.
- **Сессия до 4 часов:** double держит кадр точно. Тест формул на CPU с t = 4 ч.

**Кламп кадра:**
- **Loop:** `u = f − F·floor(f/F)`, `f0 = floor(u)`, `frac = u − f0`, `f1 = (f0+1 = F) ? 0 : f0+1`.
- **One-shot:** `fc = clamp(f, 0, F−1)`, `f0 = min(floor(fc), max(F−2, 0))`, `frac = fc − f0`, `f1 = min(f0+1, F−1)`.

**Скорость и события:**
- `speed = 0` — пауза. Отрицательная скорость: loop заворачивается, one-shot упирается в кадр 0.
- One-shot заканчивается при `f ≥ F−1` (при отрицательной скорости — при `f ≤ 0`) и стоит на крайнем кадре.
- Событие «клип закончился» срабатывает один раз, его считает тот же CPU-код (`VatEndLatch`): один раз за `Play` и
  направление. Пауза и смена скорости у конца его не повторяют, разворот повторяет на другом конце. Loop события не даёт.
- `Play` всегда начинает клип с начала (one-shot при отрицательной скорости — с последнего кадра), есть перегрузка с
  `normalizedTime`. `GetNormalizedTime`: loop — фаза текущего цикла в [0, 1), one-shot — [0, 1] (1.7).

**Интерполяция:** 2 × `LOAD_TEXTURE2D_LOD` + lerp во float, без аппаратной фильтрации — единственная работа шейдера с кадрами.

**Кватернионы** (1.8.2):
- знак выравнивает бейкер: q кадра k > 0 лежит в той же полусфере, что q кадра k − 1 того же клипа (`dot ≥ 0`),
  кадр 0 каждого клипа — как есть. Шейдер знак не проверяет: ни `?:`, ни `sign()` (`sign(0)` обнуляет кватернион);
- между кадрами — `lerp` текселей и декод, без нормализации: N и T считаются однородными формулами (§1.9) от q
  любой длины, обе с множителем `|q|²`, нормализует URP. Направление — как у nlerp; slerp не нужен: при 24° за кадр
  разница с ним меньше 0.1°;
- шов петли: если кадр вертекса за цикл делает нечётное число оборотов, q последнего кадра противоположен q первого,
  и на шаге «последний → первый» N и T проходят через ноль. Бейкер пишет предупреждение с числом таких вертексов.

**Источник времени** — только CPU. Time-нода SG не используется.

### 1.4 Состояние юнита (float4 в материале юнита)
```
_VatFrame  = (row0, row1, frac, 0)   // строки внутри блока (startRow + f0, startRow + f1) и вес второй
_VatFrameB = (row0, row1, frac, w)   // 1.8: целевой клип перехода и его вес w, вес A = 1 − w
_VatDrift  = (d + min, 0)            // 1.8.1: дрейф, уже смешанный по frac обоих клипов и по w; 1.8.3: + min 8-битных позиций
```
- **Пишет драйвер каждый кадр** (`VatCompare` сейчас, `VatAnimator` с 1.7): строки уже со `startRow`, loop, one-shot, скорость и рампы веса посчитаны на CPU. Строки — целые < 4096, во float32 точны.
- **Дрейф** считает `VatAsset.Drift(frame, frameB)`: `d = lerp(lerp(d[A.row0], d[A.row1], A.frac), lerp(d[B.row0], d[B.row1], B.frac), w)`, при `_VatFrameB = 0` — дрейф клипа A. Пишется вместе с `_VatFrame*`, когда изменился кадр; `ApplyTo` и `ApplyFrame` пишут его в превью. Дрейф одинаков для всех вертексов draw, поэтому шейдер его не читает: до 1.8.1 это были 4 выборки на вертекс на клип.
- **Шейдер не проверяет ничего:** ни диапазон строк, ни ширину, ни конечность. Корректность данных обеспечивают бейкер и CPU-код.
- **Значение по умолчанию** `(0, 0, 0, 0)` — кадр 0 первого клипа, так что материал без драйвера показывает валидную позу. В Bone тоже: строка пивотов — последняя (1.11, §1.9).
- **Постоянные ассета** (ширина текстуры, число строк) лежат в `_VatLayout` (§1.9), их пишет бейкер в шаблон.

### 1.5 Бленд и переходы
Сценарий один: клип переходит в другой клип.

**Два вида шейдера** (1.8.2, без keyword). SubGraph `vat_vertex` читает один клип (`_VatFrame`, 4 выборки на
вертекс), `vat_vertex_blend` — два (`_VatFrame` и `_VatFrameB`, 8 выборок). Так же у Bone (1.11): `vat_bone`
(две кости, 10 выборок, 1.12) и `vat_bone_blend` (18). Бленд-графы в пакете — `vat_lit_vertex_blend` и `vat_lit_bone_blend`; Unlit
и Triplanar только без бленда. Шейдер выбирает художник в шаблоне: юниты без
переходов не платят за клип B. `VatAnimator`, у которого хотя бы один VAT-материал без `_VatFrameB`, делает
`CrossFade` мгновенным (`Play`) и `_VatFrameB` не пишет. Предупреждений в лог нет (0.12.1): правила — в README.

**Шейдер с блендом.** Каждый клип считается целиком по своему `_VatFrame*` (смещение Δ, кватернион — lerp кадров), затем:
- `P = rest + _VatDrift.xyz + lerp(Δ_A, Δ_B, w)`, `N = lerp(N_A, N_B, w)`, `T = lerp(T_A, T_B, w)` — и всё. Без `?:`, `if`,
  нормализации, ортогонализации и fallback по доминантному клипу: шейдер для слабых телефонов, ветвления и выбор
  запрещены (решение пользователя в 1.8).
- Нормализует URP: вершинный проход переводит Normal и Tangent в мир через `TransformObjectToWorldNormal` и
  `TransformObjectToWorldDir`, а они вызывают `SafeNormalize` (`rsqrt(max(FLT_MIN, …))`). Противоположные N или T при
  w = 0.5 дают нулевой вектор, не NaN; у такого вертекса в этот кадр плоский свет. Риск принят: нужен разворот на
  180° между клипами и вес почти ровно 0.5.
- Ветвления по w (не читать клип с нулевым весом) нет: бленд-шейдер читает оба клипа всегда. Кому переходы не
  нужны, берёт шейдер без бленда (1.8.2).
- Блендятся готовые результаты, а не кости: бленд по костям рвёт суставы. Одна реализация на Vertex и Bone.

**Переходы (CPU, `VatAnimator`):**
- `CrossFade(clip, d)`: если предыдущий переход закончен (w = 1), целевой клип становится исходным (A := B, w = 0). Новый клип встаёт в B, его вес растёт 0 → 1 за d начиная с текущего момента.
- `Play(clip)` — мгновенная смена: B не нужен, клип пишется в `_VatFrame`, w = 0.
- `SetWeight(w, T)`: вес перехода из кода — рампа от текущего значения до w за T (T = 0 — сразу).
- `CrossFade` посреди незаконченного перехода (0 < w < 1) по сценарию не используется, но поведение определено: доминирующий клип (вес ≥ 0.5) становится исходным, новый — целевым, третий выпадает с рывком. При w = 0 или 1 рывка нет. Предупреждения в лог нет (0.12.1).
- Во время перехода скорость и пауза общие (пауза останавливает и рампу веса). `CurrentClip`, `GetNormalizedTime` и `ClipFinished` относятся к целевому клипу, исходный доигрывает молча (one-shot стоит на последнем кадре). `d ≤ 0` или NaN — переход сразу.
- `SetWeight` без целевого клипа ни на что не влияет. Вес не ограничивается: вне [0, 1] — экстраполяция поз, это ошибка вызывающего кода (0.12.1).
- Синхронизации фаз нет.

### 1.6 Материалы и батчинг
- **Копии материалов — только в Play mode и в сборке.** В edit mode `VatAnimator` материалы не трогает: шаблон показывает статичный кадр, клип и кадр выбираются в инспекторе материала. Движения в edit mode нет: время считает только драйвер в Play mode.
  Перебейк сохраняет клип, который показывает шаблон профиля, по имени (переживает смену порядка; пропал — первый клип). Отдельного клипа по умолчанию в `VatAsset` нет.
- **Копия на каждый уникальный VAT-шаблон.** В `OnEnable` `VatAnimator` собирает sharedMaterials всех своих рендереров, включая LOD, делает `new Material(template) { hideFlags = HideFlags.DontSave }` на каждый уникальный VAT-шаблон и ставит копии в слоты. Состояние пишется во все копии. Поле со списком копий — `[NonSerialized]`.
- **Уничтожение — в `OnDestroy`** (вызывается при `Destroy`, выгрузке сцены и выходе из Play mode). Пулинг через `SetActive` копии не пересоздаёт.
- **Play On Enable** при каждом `OnEnable` запускает клип с начала: поле Clip компонента, пустое — первый клип ассета. Юнит из пула стартует заново (1.7).
- **Экипировка** — отдельный меш, скиннённый на кости того же рига (например, 100% на кость руки), со своим VAT-материалом на той же bone-текстуре. Юнит пишет в него то же состояние.
- **Никогда `renderer.material`**: он сам клонирует материал, и копия утекает.
- **MaterialPropertyBlock запрещён.** Эффекты юнита (hit-flash, цвет команды, dissolve) пользователь пишет сам во все копии из `VatAnimator.Materials`: обёрток `SetFloat/SetColor/SetVector` и dev-проверки `HasPropertyBlock()` нет (0.12.1, пакет — конструктор). Hit-flash в VatDev проверяется через `_BaseColor` шаблона, эмиссии в графах нет (1.7).
- **SRP Batcher.** Разные материалы с одним вариантом шейдера дешёвы, но это всё равно отдельный draw на рендерер в каждом проходе. Бюджет — по замеру в 1.14. «Enable GPU Instancing» на VAT-материалах выключен.
- **Варианты шейдера.** Каждый шейдер (Vertex и Bone, с блендом и без, 1.8.2, 1.11) — отдельный батч; у Bone один вариант — две кости на вертекс (1.12, решение пользователя), ключей нет. Число вариантов в сцене — забота художника: валидатора сборки нет (1.10).
- **Свойства состояния (`_VatFrame*`) — scope Hybrid Per Instance**, с «Promote to final Shader» в SubGraph. В обычных вариантах они попадают в `UnityPerMaterial` и совместимы с SRP Batcher, а путь DOTS нужен BRG-рендереру из патча 2 без переделки шейдеров.
- **Текстуры — Per Material**, Blackboard-свойства.
- **Запись каждый кадр** у играющих юнитов: `_VatFrame` и `_VatDrift` на материал юнита, у бленд-шаблона ещё `_VatFrameB`. Стоимость меряется в 1.14, маркер профайлера — `VatAnimator.Write`. Если кадр не изменился (пауза, законченный one-shot), запись пропускается.
- **Не реализовывать `OnBecameVisible` и `OnWillRenderObject`**: они исключают объект из GRD, а он понадобится в патче 2.

### 1.7 Меш
Раскладка задаётся явно через `SetVertexBufferParams`, меш non-readable. Два потока (для IDVS на Mali): в потоке 0 позиция и кости, в потоке 1 всё остальное. Атрибуты по каналам — в карте §1.9.

Правила:
- **Выбор влияний** (1.12): как Unity при Skin Weights = 2 Bones — первые два слота веса в порядке меша, без сортировки, нормализация к сумме 1; вертекс без весов — 100% на корневую кость, одна кость — оба слота на ней. Проба в 6000.4: Unity берёт первые N слотов как записаны (неотсортированные тоже), при 2 Bones перенормирует их (0.5/0.3 → 0.625/0.375), при 4 Bones — нет; при равных весах решает порядок слотов, а не меньший индекс. Импорт FBX кладёт веса по убыванию, так что это «два наибольших». Сверяет тест против `BakeMesh`.
- **Никогда UInt или SInt на TexCoord**: через float4 в SG они приходят сырыми битами.
- **Кости — в TexCoord6** (1.11). TEXCOORD4 и TEXCOORD5 занимает проход MotionVectors URP (`positionOld`, `alembicMotionVector`): `uv4` в графе с другим типом не компилируется. TexCoord6 не пересекается и с `uv1`/`uv2` лайтмапов.
- **UV в SubGraph проходят через `half4`:** Shader Graph объявляет UV-каналы в привязках сабграфа как `half4` при любой точности графа и нод. Поэтому в канале только значения, точные в fp16: байты UNorm8 (шаг 1/255 больше ошибки fp16), целые до 2048 во Float16. UNorm16 `i/65535` в fp16 путает соседние кости от 1024. **Выражения от этих UV GPU тоже считает в half**, хотя Custom Function объявлена с `float` (1.12, видно в редакторе на D3D11): `hi·256 + lo = 65535` переполняло half (65504) и давало бесконечность у вертексов с весом 1. Промежуточные значения держать ≤ 65504: вес — `dot(bytes, (256, 1) / 65535)`.
- **После бейка вершины не переставляются**: никаких `Mesh.Optimize`, `OptimizeReorderVertexBuffer` и сторонних оптимизаторов. Mesh LOD — только после проверки, что вершинный буфер не переставлен (1.18).

### 1.8 Ассеты
- **Формат — `.asset`**: главный объект `VatAsset` и sub-assets Mesh и Texture2D. На `VatAsset` стоит `[PreferBinarySerialization]` (проект в Force Text, без атрибута пиксели пишутся hex'ом).
- **Текстуры:** `new Texture2D(w, h, GraphicsFormat.R16G16B16A16_SFloat | R8G8B8A8_UNorm, TextureCreationFlags.None)` → `SetPixelData` → `Apply(false, true)` → `AddObjectToAsset`. Point, Clamp, без мипов. Конструктор с `TextureFormat` и `linear = false` даёт sRGB и портит байты — не использовать.
- **Повторный бейк — на тех же объектах:**
  1. новые Texture2D и Mesh собираются в памяти readable и целиком проверяются;
  2. `EditorUtility.CopySerialized(новый, существующий)` для каждого sub-asset'а;
  3. `m_IsReadable = false` через SerializedObject, затем `SaveAssets`.

  Пока шаг 1 не пройден, старый ассет не трогается. Так fileID и ссылки из материалов и префабов сохраняются даже при смене размеров (проверено на 6000.3).
- **Версия формата.** `VatAsset` хранит `formatVersion`, описание раскладки по §1.9 (число элементов, ширина, блоки, строки; у Bone `totalRows` включает строку пивотов) и режим (`VatMode`: Vertex или Bone, 1.11; у Vertex-ассета, испечённого вместо Bone, — причина отката) и хэш исходника и настроек бейка. Рантайм отказывается играть неподдерживаемую `formatVersion` с понятной ошибкой. Инспектор ассета и карточка Result профиля показывают «бейк устарел», если хэш, посчитанный по профилю сейчас, не совпадает с хэшем в ассете (1.10); профиль с проблемами хэша не даёт.
- **Память в инспекторе** (1.10): фактические width×height×bytes каждой текстуры (по `Texture2D`), padding последнего блока и доля каждого клипа; LOD добавит 1.18. Это GPU-память сборки: `Profiler.GetRuntimeMemorySizeLong` даёт её плюс заголовок объекта (около 0.9 КБ). Memory Profiler редактора может показать вдвое больше: после любой записи в AssetDatabase (`CreateFolder`, `CreateAsset`, `SaveAssets`) редактор держит CPU-копию у всех загруженных текстур, даже у обычных PNG, до их выгрузки. Сверять со сборкой. Бюджет считается по уникальным ассетам.
- **Баунды** (`Mesh.bounds` и `SubMeshDescriptor.bounds`):
  - **Vertex:** объединение позиций по всем кадрам — между кадрами позиции интерполируются линейно и из оболочки не выходят;
  - **Bone и Rigid:** объединение капсул радиуса `s_max·ρ` вокруг отрезков, по которым между кадрами движутся пивоты (ρ — наибольшее расстояние вершины кости от пивота в bind-позе). С 1.11 радиус берётся на каждый вертекс (`s_max · |v − p̃|`) — это та же оболочка, только плотнее; AABB капсулы = AABB пивотов кости по кадрам ± радиус;
  - бленд клипов в объединение по клипам уже входит.

### 1.9 Карта каналов
Единственное место, где описано, что лежит в каждом канале. Остальные разделы ссылаются сюда.

**Текстуры.** Все — Point, Clamp, без мипов, linear. Адрес тексела — по §1.1: `x` — элемент, `row = b·totalRows + startRow + frame`.

| Текстура | Режим | Формат | Элемент x | R | G | B | A |
|---|---|---|---|---|---|---|---|
| `_VatPosTex` | Vertex | RGBAHalf или RGBA8 (1.8.3) | вертекс | Δ.x | Δ.y | Δ.z | 0 |
| `_VatRotTex` | Vertex | RGBA8 | вертекс | q.x | q.y | q.z | q.w |
| `_VatBoneTex`, кадры | Bone, Rigid | RGBAHalf | 2i | Δ.x | Δ.y | Δ.z | s |
| `_VatBoneTex`, кадры | Bone, Rigid | RGBAHalf | 2i + 1 | q.x | q.y | q.z | q.w |
| `_VatBoneTex`, последняя строка | Bone, Rigid | RGBAHalf | 2i | p̃.x | p̃.y | p̃.z | 0 |
| `_VatBoneTex`, последняя строка | Bone, Rigid | RGBAHalf | 2i + 1 | 0 | 0 | 0 | 1 |

- **Vertex:** `Δ = pos − rest − d`. Строки — только кадры: `totalRows = ΣF`, первый клип с `startRow = 0`.
- **8-битные позиции** (1.8.3, `formatVersion` 6): `b = round((Δ − min) / size · 255)`, при size = 0 байт 0; шейдер —
  `pos = rest + _VatDrift.xyz + t · _VatPosScale.xyz`, где `_VatDrift = d + min`, `t` — выборка (у half сам Δ, size = 1,
  min = 0). Формат и `VatPositionRange` хранит `VatAsset`.
- **Дрейф:** не текстура, а `Vector3[]` в `VatAsset` (float32, строка `startRow + frame`, длина `totalRows`). CPU смешивает d по кадрам и переходу и пишет `_VatDrift` (§1.4), шейдер: `pos = rest + _VatDrift.xyz + lerp(Δ0, Δ1)`. Дрейф есть в каждом Vertex-ассете и включён всегда (§2.2).
- **Bone и Rigid:** `i` — индекс кости или куска, элементов `E = 2·N`, блок всегда один (N ≤ 2048, `W = 2N`). Клипы
  начинаются со `startRow = 0`, как в Vertex; последняя строка — пивоты: `totalRows = ΣF + 1`, шейдер читает её как
  `_VatLayout.y − 1` (1.11). Так `_VatFrame = 0` и `_VatFrameB = 0` — кадр 0 первого клипа, а не строка пивотов
  с нулевым q (с пивотами в строке 0 бленд-шейдер без перехода делил на `|q|² = 0` и получал NaN). Второй тексел
  строки пивотов — единичный q: `q = 0` не пишется нигде. `p̃` — пивот, округлённый до half; `Δ = p_pose − p̃`;
  `s` — равномерный масштаб, `s = 0` — кусок скрыт.
- **Скиннинг в шейдере** (1.11, без `normalize`): `rot(q, v) = (w² − |u|²)·v + 2(u·v)·u + 2w·(u × v)` — однородная
  формула, равна `|q|²·R·v` при любой длине q; `pos = rot(q, v − p̃)·(s / |q|²) + p̃ + Δ`, `N = rot(q, n)`,
  `T = rot(q, t)` без нормализации (её делает URP, как в Vertex). q и (Δ, s) — `lerp` двух кадров.
- **Кватернион** — (x, y, z, w), w — скалярная часть. В Vertex он задаёт кадр (T, N×T, N): `N = rot(q, (0,0,1))`, `T = rot(q, (1,0,0))`, знак бинормали — `tangent.w` меша.
- **`_VatRotTex`** (1.8.2, `formatVersion` 5): кватернион целиком, знак выровнен по соседним кадрам (§1.3).
  - байт компоненты `b = round(c·127) + 128` (от 1 до 255), 0 и ±1 точные; декод `q = t·255/127 − 128/127`, где
    `t = b/255` — значение выборки; ошибка поворота до 0.9° (до 1.8.2 smallest-three 2+10+10+10 давал 0.2°);
  - однородные оси: `N = (2(xz + wy), 2(yz − wx), w² − x² − y² + z²)`, `T = (w² + x² − y² − z², 2(xy + wz), 2(xz − wy))`,
    у неединичного q обе длины `|q|²`, ортогональность сохраняется.

**Меш**

| Поток | Атрибут | Формат | Содержимое |
|---|---|---|---|
| 0 | Position | Float32×3 | позиция покоя: rest в Vertex, bind-поза в Bone, исходная в Rigid |
| 0 | TexCoord6 | UNorm8×4 (Bone, 1.12) | `(i0/255, i1/255, w_hi/255, w_lo/255)` — две кости и 16-битный вес первой |
| 1 | Normal | Float16×4 | нормаль покоя, w = 0 |
| 1 | Tangent | Float16×4 | тангент покоя, w = знак бинормали ±1 |
| 1 | TexCoord0 | Float16×2 | UV |

- **Вес:** `w0 = round(z·255)·256/65535 + round(w·255)/65535` (так, без промежуточного 65535, §1.7), `w1 = 1 − w0`; `pos = lerp(P1, P0, w0)`, N и T — то же от `rot(q, n)/|q|²` (деление на `|q|²` уравнивает вклад двух костей).
- **Индексы:** `i = (uint)(uv.x·255 + 0.5)` и `(uint)(uv.y·255 + 0.5)`; до 256 костей (1.12, решение пользователя;
  в 1.11 был один индекс Float16 до 2048). Rigid (1.15) с этим форматом — до 256 кусков; больше — решать в 1.15.
- **В Vertex-режиме TexCoord6 нет.** Vertex color и дополнительные UV не переносятся.
